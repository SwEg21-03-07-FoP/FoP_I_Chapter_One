Chapter One
Basic Concepts of Programming

Problem analysis, algorithm design, pseudocode, flowcharts, and an overview of languages and paradigms.

New to programming? Start hereYou need no prior knowledge. Read each section in order, and look for the shaded boxes like this one: they explain the ideas in plain words with everyday examples. Do the exercises with pen and paper before opening the answers. This chapter has no real code yet. It teaches you to plan a solution, which is the most important programming skill. A short glossary and self-check questions are at the end.

1. Basics of program development

Computer program

A self-contained set of explicit, unambiguous instructions telling the computer what to do and how.

Computer programming

Also called coding: writing, testing, debugging, troubleshooting and maintaining source code.

Software development life cycle

The overall process of developing software, from planning to maintenance.
In plain wordsA program is like a recipe. A recipe lists ingredients and exact steps, and a cook follows them without guessing. A computer is a very fast cook that does exactly what the steps say, nothing more. If a step is unclear or missing, it will not guess what you meant. That is why the instructions must be explicit and unambiguous.

Why study programming?

1. Great job prospects

  • Computers run phones, banks, hospitals and farms, so almost every organization needs people who can build and maintain software.
  • Example: a mobile-money service, a bus-ticketing app and a hospital records system all need programmers, testers and analysts.

2. It makes life easier

  • You can automate repetitive work.
  • Example: a short program adds columns 2, 3 and 4 of a spreadsheet and finds the average every day, instead of doing it by hand.
  • Example: an auto-reply that spots “Hi” in a message and answers “Hi! What’s up?”

3. Structured, creative thinking

  • Programmers break a problem into small pieces before coding, a habit that helps in any area of life.
  • Example: Facebook began as a way for students to find out about each other, and Google as a way to organize the world’s information. Both started with a problem that programming could solve.

4. Persistence

  • You write, run and debug a program many times before it works, and learn that hard problems usually have a solution.
  • Example: your program prints the wrong total. You trace it, find the counter started at 1 instead of 0, fix it and run it again.

5. You learn how to learn

  • One missing symbol can break a program, so you become detail-oriented.
  • You learn to search for methods on your own.
  • Example: finding out by yourself how to sort a list of names.

6. Entrepreneurship

  • You can build your own ideas without paying for every step, and you understand programmers’ work when you hire them.
  • Example: a shop owner builds a simple online order page.
  • Skills like SQL and HTML/CSS help marketers and designers too.

Program development life cycle

  1. Planning: gather information from stakeholders; decide what is feasible.
  2. Requirements analysis: collect and document requirements.
  3. Design: create the architecture of the system and its elements.
  4. Implementation: build the software in a programming language.
  5. Testing and integration: evaluate quality; find and fix defects.
  6. Maintenance: update and support the software after release.
In plain wordsThe life cycle is how a team builds software without chaos, much like building a house: decide what you can afford (planning), ask the owner what they need (requirements), draw the plans (design), build (implementation), inspect (testing), and repair and improve over the years (maintenance). Real projects often loop back to earlier steps when something changes. As a beginner, you will mostly practice the middle steps on small programs.

A deeper look at the life cycle

The work is organized into three overlapping phases:

  • Development and design: analysis, design, coding and testing.
  • Documentation: starts during design and continues to the end.
  • Maintenance: keeps the program useful until it is retired.
Feasibility study: is the project worth doing?
  • Organizational: does it support the organization’s goals?
  • Economic: will it save money or raise income?
  • Technical: do we have the hardware, software and network?
  • Operational: will users and management accept it? Does it meet customer and government requirements?
Requirements analysis
  • Find the input, processing and output (what must be done, not how).
  • Talk to the users and involve them throughout.
  • Record the requirements in a document.
Design
  • Design the solution as an algorithm: the blueprint of the system.
  • Review it with users before coding.
  • Catches mistakes before they are built in.
Coding (implementation)
  • Translate each algorithm step into the chosen language.
  • Also set up databases and networks.
  • Train the people who will use it.
Testing and debugging
  • Testing checks whether the program is correct; debugging finds and fixes the errors (bugs).
  • Testing every case is impossible, so choose test data carefully. Good teams plan test data before coding.
  • Unit testing: each small part on its own.
  • Integration testing: parts combined, to check they work together.
  • System testing: the whole system on its real platform.
  • Acceptance testing: does it do what the user needs?
Documentation: five key documents
  • The algorithm and its changes
  • A program description
  • A well-commented program listing
  • Sample test runs
  • A users’ manual
Maintenance: usually the longest phase
  • Repair bugs found later.
  • Revise for new needs, such as organizational change.
  • Upgrade with new features or new technology.
  • Development takes days or months; maintenance can last years. Good documentation makes it cheaper.

Real-world example: a school results system

A school wants teachers to enter students’ marks and print report cards automatically, instead of calculating everything by hand. Here is how each phase of the life cycle applies.

  1. Planning and feasibility
    • What happens: before anyone writes code, the team decides whether the project is worth doing.
    • In the school: the principal and teachers explain the problem. Working out totals and averages by hand takes hours, and mistakes are common.
    • Feasibility questions: Do we have enough computers? Can the school afford the project? Will teachers actually use it?
    • Why it matters: it stops the school from spending time and money on a system nobody can use.
  2. Requirements analysis
    • What happens: the team finds out exactly what the program must do, not how.
    • Input: each student’s name and marks per subject.
    • Process: add the marks (total), divide by the number of subjects (average), then rank the students.
    • Output: a printed report card for each student.
    • Talking to users: teachers say they must be able to correct a wrong mark, and parents want a paper copy.
    • Why it matters: everything is written in a requirements document. If the team misunderstands the need now, it will build the wrong thing.
  3. Design
    • What happens: the solution is planned on paper first, like an architect’s drawing before a house is built.
    • The algorithm: read the marks, then total = sum of the marks, then average = total ÷ number of subjects. If average is 50 or more, the result is “pass”, otherwise “fail”.
    • Pictures: draw a flowchart of these steps and sketch what the report card will look like.
    • Review: teachers look at the design. Fixing a drawing is far cheaper than fixing a finished program.
  4. Implementation (coding)
    • What happens: programmers turn each design step into instructions in a programming language.
    • In the school: they also build a database, which is the place where names and marks are stored.
    • Getting ready to use it: install the program on the school computers and train the teachers. A program nobody knows how to use is not useful.
  5. Testing
    • What happens: the team tries the program with sample data whose correct answer is already known. If the program gives a different answer, it has found a bug.
    • Unit test (one small part): marks 60, 70 and 80 should give an average of 70.
    • Integration test (parts together): marks typed into the entry screen must appear correctly on the report card.
    • System test (the whole thing): run all 500 students on the school’s own computer. Is it fast enough?
    • Acceptance test (the user decides): one real class of teachers tries it and confirms it does what they need.
  6. Maintenance
    • What happens: software is never really “finished”. After the school starts using it, it still needs care.
    • Repair: a bug is found when a teacher leaves a mark blank. The team fixes it.
    • Revise: the education authority changes the grading scale, so the program is updated.
    • Upgrade: the school asks for a new feature, such as sending results to parents by text message.
    • Why it matters: this phase can last for many years, much longer than building the program.

Notice that documentation (manual, test runs) is produced along the way, not at the end.

2. Problem analysis

A problem is the gap between the existing and the desired situation. Problem solving transforms a problem description into a solution, and programming is a form of problem solving:

  1. Problem analysis: understand the problem; identify input and output.
  2. Algorithm design: design the solution.
  3. Coding: write a program matching the algorithm's steps.

Input

What data are available?

Process

What method leads from the data to the results?

Output

What results must the program produce?

Why analyze? To understand the real-world problem and user needs, and to validate abstract solutions before development.

Example: average of two numbersInput: two numbers, say 6 and 10. Process: add them, then divide by 2. Output: 8. Whenever you meet a new problem, write down these three things before anything else. Many beginners skip this and start coding too early, and then get stuck because they are not sure what the program should produce.

More on analysis

  • Basic analysis (always needed): extract the input, processing and output.
  • Extended analysis (if basic is not enough): gather more information until you fully understand the problem.
  • Focus on what must be done, not how.
  • Record the requirements and involve the users.

Two ways to attack a big problem

Top-down

Start with the whole problem and split it into parts. If a part is still too big, split it again. Solve the small parts, then merge the solutions. Example: class average splits into read the marks, add them, divide by the count, print.

Bottom-up

Start by solving the smallest practical parts, then merge them step by step into the final solution. Example: to compute M = √4 + ∛4 + ⁴√4, first find each root, then add the three results.

The main difference is splitting versus merging.

3. Algorithm design

An algorithm is a well-defined, finite, step-by-step set of instructions that solves a problem or class of problems. It is independent of any programming language. A computer is an "algorithm-responding" machine: it needs detailed step-by-step instructions.

CharacteristicMeaning
DefinitenessEach instruction is clear and unambiguous.
FinitenessIt terminates after a finite number of steps.
InputZero or more inputs.
OutputAt least one well-defined output.
EffectivenessEach instruction is basic enough to be carried out.

Pseudocode

Description of what a program must do in natural language and math symbols; a semi-programming language.

Flowchart

Graphical representation: boxes of various kinds, ordered by connecting arrows.
Example: an algorithm for making tea1. Boil water. 2. Put a tea bag in a cup. 3. Pour the water into the cup. 4. Wait 3 minutes. 5. Remove the tea bag. 6. Stop.
Check it against the characteristics: every step is clear (definiteness), it ends (finiteness), its inputs are water and a tea bag, its output is a cup of tea, and each step is something you can actually do (effectiveness). An instruction like "make it taste nice" would fail, because it is not definite. A step like "keep stirring forever" would fail, because it never ends.

Pseudocode or flowchart?They describe the same algorithm. Pseudocode is written text and is quick to write. A flowchart is a picture and is easier to follow at a glance. There is no single correct format, so aim for clear, simple steps.

What makes a good algorithm?

  • Precise: no unclear steps.
  • Simple: easy to follow.
  • Correct: right result for all valid inputs.
  • Efficient: does not waste time or memory.
  • One problem can have many algorithms. Choose one that is easy to maintain and efficient.

Pseudocode: less formal and more formal

Pseudocode has no fixed standard. It is not executable, and you may write it informally or formally. Here is the same task, read two integers and print their sum, written both ways. The arrow ← means assign.

Less formal
1 Start
2 Ask the user for the first integer
3 Ask for the second integer
4 Work out the sum
5 Display the sum with a message
6 Stop
More formal
1 Start
2 Read n1
3 Read n2
4 sum ← n1 + n2
5 Print sum
6 Stop

Choosing: largest of two or three numbers

Largest of two
Read n1, n2
if n1 > n2 then
    Big ← n1
else
    Big ← n2
Print Big
Largest of three
Read n1, n2, n3
if n1 >= n2 and n1 >= n3 then
    Big ← n1
else if n2 >= n3 then
    Big ← n2
else
    Big ← n3
Print Big

Using >= means ties (for example 5, 5, 3) still give the right answer.

4. Flowchart symbols

NameSymbolUsage
Start / Stop (terminal)The beginning and end points.
ProcessAn instruction or operation to carry out.
DecisionA yes/no question with two exits (True and False).
Input / OutputRead data or print a result.
Connector (on page)Jump between points on the same page, avoiding crossing lines.
Connector (off page)The chart continues on another page.
Flow arrowConnects symbols and shows the direction of flow.

Two kinds of flowchart

  • System flowchart: the overall logic of a data-processing system.
  • Program flowchart: the operations and decisions inside one program. This chapter uses this kind.
  • Like pseudocode, a flowchart does not depend on any language.

Decision and connectors

  • Decision: a diamond holding a question. It has two exits (True and False), and only one is followed each time.
  • Connectors: a small circle with a letter links two points on the same page. A pentagon-like shape shows that the chart continues on another page.

Conventions to follow

  • Initialize sums and counters to zero.
  • Show assignment with a left arrow (sum ← sum + x).
  • Mark the beginning and end of every decision and every repetition, and state its condition.
  • Clearly indicate where the algorithm ends.

5. Worked problems and exercises

Problem 1: area and perimeter of a rectangle

Input: Length, Width · Process: Area = L × W; Perimeter = 2 × (L + W) · Output: Area, Perimeter
Start
Read L, W
area = L * W
perimeter = 2 * (L + W)
Print area, perimeter
End

Problem 2: total salary

Input: Salary, Overtime
Total_Sal = Salary + Overtime
Output: Total_Sal

Problem 3: sum of even numbers from 2 to 30

Start
counter = 2, sum = 0
while counter <= 30
    sum = sum + counter
    counter = counter + 2
print sum
End

Loops: the four parts

A loop repeats steps until a condition says stop. A well-formed loop has four parts:

  • Initialization: set starting values (Problem 3: counter = 2, sum = 0).
  • Computation: the work done each pass (sum = sum + counter).
  • Test: every loop needs a way out, or it runs forever (counter <= 30).
  • Update: change the counter so the test can eventually fail (counter = counter + 2).

Worked example: average of a set of values

total ← 0
tally ← 0
for each sample
    total ← total + sample
    tally ← tally + 1
average ← total / tally
print average

Worked example: largest and smallest of 50 values

Read first number N
MAX ← N, MIN ← N, count ← 1
while count < 50
    Read next number N
    if N > MAX then MAX ← N
    if N < MIN then MIN ← N
    count ← count + 1
Print MAX, MIN

Idea: assume the first number is both the largest and smallest, then compare each new number with the best so far.

Trace Problem 3 by handTo check an algorithm, act as the computer and track each variable on paper. This is called a trace table. The loop begins with counter = 2 and sum = 0. Each pass adds the counter to the sum, then adds 2 to the counter. Before every pass, the computer asks: is the counter still 30 or less?

After pass 15 the counter becomes 32, the question "is counter <= 30?" is answered No, and the loop stops. The program prints 240. Always set your starting values (initialize) before the loop, or the result will be wrong.

A method for any exercise:1. Write input, process and output. 2. Write the steps in pseudocode. 3. Test with a small example by hand. 4. Only then draw the flowchart.

Try it yourself

Write your own pseudocode or steps first. The model solution unlocks only after you submit an attempt.

6. Programming languages

A programming language is an artificial language used to control a computer. Like natural languages, it is defined by syntactic and semantic rules. Low-level: machine and assembly. High-level: C, C++, Java.

Gen.TypeTraits
1stMachine language0s and 1s; long and difficult
2ndAssembly languageAssembles repetitive instructions; shorter code
3rdProceduralInclude commands; shorter code
4thNonproceduralApplication generators; commands specify results
5thIntelligentNatural-language style

Progress runs from machine-oriented to human-oriented language. There are over 2,400 programming languages.

The five generations in more detail

1st generation: machine language (1940s)
  • The only language a computer understands directly: zeros and ones.
  • Each instruction has an op code (what to do) and an address (where the data is).
  • Fast, memory-efficient, full hardware control.
  • Very hard to write, and different on each type of computer.
2nd generation: assembly language (early 1950s)
  • Short symbols (mnemonics) such as ADD or LOAD instead of binary.
  • An assembler translates it to machine code.
  • Easier than binary, but still machine-dependent and not portable.
  • Used mainly in system software.
3rd generation: high-level languages (1950s to 1970s)
  • English-like and machine-independent, for example Z = A + B.
  • Easier to write and debug, but must be translated to machine code.
  • Procedural: you say what to do and how.
  • Examples: C++, FORTRAN, COBOL, BASIC.
4th generation (since late 1970s)
  • Non-procedural: you state the result you want, not the steps.
  • Easier to write, but you have less control over how it is done.
  • Examples: SQL, report generators, application generators.
5th generation (1990s)
  • Close to human speech, such as “get me a customer’s sales figure for last year”.
  • Used in artificial intelligence and expert systems.
  • Needs powerful hardware and software.

The higher the level, the easier a language is for people. Machine and assembly languages depend on the computer. High-level languages do not.

In plain wordsThe computer only understands machine language, which is 0s and 1s. Humans write in higher-level languages that are easier to read, and special programs (compilers or interpreters) translate them for the machine. Which language should you pick? For this course, any popular one works: the thinking skills in this chapter apply to all of them. Think of languages as different tools for the same job, like different brands of hammer.

7. Programming paradigms

A paradigm is a style, or "way", of programming. It is not tied to one language, and languages may follow several paradigms.

ParadigmDescriptionModelExamples
Imperative (procedural)Statements directly change stateAlgorithms + dataC, C++, Java, PHP, Python, Ruby
Logical (declarative)Defines logic, not control flowFacts + rulesProlog, SQL, CSS
FunctionalEvaluation of mathematical functions; avoids stateFunctions of functionsC++, Lisp, Python, JavaScript
Object-orientedObjects manipulated through methodsObjects + messagesC++, C#, Java, PHP, Python

The paradigms in more detail

Unstructured (sequential)
  • Commands run in order, one per line, and execution can jump to any numbered or labeled line.
  • The whole program is one block, so it is hard to change and debug.
Procedural
  • A procedure (routine, subroutine, method or function) is a named set of steps you can call from anywhere, and control returns to the caller afterwards.
  • Code can be reused without copying.
  • Easier to follow than GO TO jumps, which can create tangled “spaghetti code”.
  • A correct procedure stays correct, so errors are easier to find.
  • Examples: C, Pascal, FORTRAN.
Modular (structured)
  • A discipline within procedural programming.
  • Procedures with a common purpose are grouped into modules, each written and tested on its own.
  • Scoping stops one procedure from touching another’s variables.
Functional
  • Computation is the evaluation of mathematical functions.
  • Values are not changed; they are turned into new values.
  • Same input always gives the same output, with no side effects. Recursion is common.
  • Examples: Lisp, Scheme.
Logic
  • You state facts and rules; the system works out the answers.
  • Prolog example: X is the brother of Y if they share a father F and a mother M, and X is male.
brother(X,Y) :- father(F,X), father(F,Y),\n                mother(M,X), mother(M,Y), male(X).
Object-oriented (OOP)
  • A program is a collection of cooperating objects.
  • Each object bundles data with the functions that use it (encapsulation), and objects send messages to each other.
  • Benefits: reuse through inheritance, data hiding, and an easy match to real-world things.
  • Examples: Java, C++, Smalltalk.
Procedure-oriented (POP)Object-oriented (OOP)
Program divided into proceduresProgram divided into objects
Global data shared by many functionsData tied to the functions that use it and protected
Data moves freely between functionsData is hidden
Hard to add new data and functionsEasy to add new data and functions
Top-down approachBottom-up approach
In plain wordsParadigms are different styles of giving instructions. Imperative: you tell the computer exactly what to do, step by step, like a recipe. Logical or declarative: you state what you want, and the system works out how (a database query asks for what you want, not how to search). Functional: you build the result by combining small functions, like a chain of calculators. Object-oriented: you model things as objects that hold data and can do actions, such as a Student object with a name and a method to enroll. You do not need to master these now. Just know they exist, because you will meet them in later courses.

Glossary for beginners

Source code
The text of a program, written by a programmer.
Debugging
Finding and fixing mistakes (bugs) in a program.
Stakeholder
Anyone affected by or interested in the software, such as users, clients and managers.
Variable
A named place that stores a value, such as sum or counter.
Initialize
Give a variable its starting value.
Loop
A set of steps that repeats while a condition is true.
Syntax
The spelling and grammar rules of a language.
Semantics
What a statement means or does.
Feasibility study
An early check of whether a project is worth doing (organizational, economic, technical, operational).
Pseudocode
An informal, language-independent way to write an algorithm in plain steps.
Procedure (function)
A named set of steps you can run from anywhere in a program.
Module
A group of related procedures that can be written and tested separately.
Encapsulation
Keeping data and the functions that use it together inside an object, hidden from outside.
Top-down / bottom-up
Splitting a big problem into parts, or building a solution from the smallest parts.
Heuristic
A rule of thumb or guess. Computers need exact steps, not guesses.
